# MiniMax H3：4 台 DGX Spark Ring4「先跑通、再好用」执行补充

日期：2026-09-18  
适用对象：在用户机器上执行部署的 Agent 或工程人员。

## 1. 当前目标，不再更换方向

本阶段只交付：**四台 DGX Spark 无高速交换机直连，四个 rank 共同完成一个 MiniMax H3 视频任务，并能反复使用。**

优先级：正确生成 → 可重复与可恢复 → 满足日常输入方式 → 测量真实速度 → 后续优化。

单机、双机只作为排障检查点，不作为本阶段的替代交付。暂不转向四个独立实例、两组双机、Sol-H3、其他视频模型或性能排名。若当前组合存在阻塞，应提交证据、提出维持四机目标的最小修复，而不是把另一种部署称作 Ring4 成功。

本文件是执行目标与验收补充，不是重新编写的运行时，也不宣称已在用户的 GB10、RDMA 网络上测试。新增的排队、状态、恢复要求尚需本地执行人员实现或验证。

## 3. 第一轮配置边界

| 项目 | 第一轮选择 |
|---|---|
| 物理目标 | 4 台 Spark、4 个 rank、无高速交换机物理环 |
| 并行候选 | SGLang Native，TP1 × Ulysses1 × Ring4；SP=4 |
| 编码器 | `replicate` |
| 首轮模型 | 官方 MiniMax H3，`fl2va` 分区 |
| 先完成的任务 | T2VA 文生音视频，再完成单张首帧 FL2VA |
| Attention | 固定快照的 FA 路径，先验证 GB10 内核与 LSE |
| 精度候选 | 原文档 DiT FP8；记录实际量化组件，不标注“全模型 FP8”或“无损” |
| 执行 | eager，首轮不引入编译、缓存、蒸馏、稀疏 attention 或第三方编码器 |
| 负载 | 整个四机组最多 1 个活跃生成任务，其他任务排队 |
| 正式输出基线 | 请求 4 秒、短边 768、50 步，记录真正输出的宽高、帧率、时长 |

这是**待验收候选配置**，不是“这样填就必然成功”的承诺。[R1]

本次重新读取原文档固定源码 `e970453b433e1467e22f6d925f270563417540b5`，其 H3 校验明确要求 `Ring > 1` 使用 FlashAttention；`quality="high"` 的审计条件是特定 4×H200 部署，不适用于本方案。不要删除校验来强行启动，也不要用 cuDNN 替换后仍声称相同 Ring 路线。[R2]

原文档 `quality="lossless"` 保持不变；它是运行时策略字段，不代表 FP8 数学无损。[R1][R2]

### 配置允许怎样修复

用户固定的是“四机共同生成”的目标，不是任何可能有问题的环境参数。发现版本、装载或内核问题，可以提出最小补丁，但必须保留原版本、记录 diff、说明原因、四台同步并重跑受影响检查。

`--performance-mode speed` 不是不可修改的验收条件。若它导致装载或内存问题，应核对固定源码的组件驻留策略，再测试受支持的替代设置，不能为了保留名称牺牲正确性。固定源码将 DiT 自动逐层 offload 的可用模式声明为 `auto` / `memory`；这不证明切到该模式就能在 Spark 上成功，也不证明更快。[R2]

### 缩小单机、双机验收的范围

原文档安排单机和双机也执行完整质量对照。为了先到达四机可用，本阶段允许把它们的完整性能对照移到后面，但**不跳过组件加载、内核、通信和基本音视频链路检查**。

高分辨率单机 OOM 要区分原因：权重或必需组件无法装载，与长序列激活峰值过大，不是同一问题。不能认定 Ring4 一定解决前者；也不能仅凭后者就判定四机一定不可行。保留证据后，按受控配置验证 Ring2 / Ring4 的真实峰值，不用“总内存除以四”推导。[R1]

## 5. 四机启动与第一次正式提交

**仅当原文档所需配置已填写、镜像与模型已验收、旧模型已通过实际管理入口安全暂停时执行。** 以下命令复用原 ZIP，不是无需准备的一键安装命令。

四台分别确认自己的 `NODE_RANK` 为 0、1、2、3。结束之前的单机或双机 H3 测试服务，确认没有残留模型进程。四台各执行一次：

```bash
cd "$HOME/h3-ring-kit"
bash scripts/run_node.sh serve 4
```

不要再在这条命令外套四进程 `torchrun`，也不要在每台分别提交视频任务。[R1]

四台初始化完成后，仅在 S0 另开终端：

```bash
cd "$HOME/h3-ring-kit"

# 冒烟只确认链路，不作为可用画质验收。
python3 scripts/video_client.py \
  --request requests/smoke.json \
  --out /srv/h3-ring/output/four-smoke.mp4

# 只在上一条完成、输出检查通过后执行正式请求。
python3 scripts/video_client.py \
  --request requests/quality.json \
  --out /srv/h3-ring/output/four-quality.mp4
```

重复测试使用不同输出文件名，保留每条 job ID、请求和结果。正式请求文件为原文档 4 秒、短边 768、50 步设置；若接口拒绝字段，先对照本镜像实际 schema 修正并记账，不让参数被静默忽略。[R1]

若宿主机已有 ffmpeg / ffprobe，执行完整检查；没有则按原文档使用运行时镜像检查，不必为了工具替换宿主机环境：

```bash
ffprobe -v error -show_streams -show_format -of json \
  /srv/h3-ring/output/four-quality.mp4 \
  > /srv/h3-ring/output/four-quality.ffprobe.json

ffmpeg -v error -i /srv/h3-ring/output/four-quality.mp4 -f null -
```

`ffprobe` 成功不等于画面可用。还须播放、听音，检查非预期黑屏、持续静止、花屏和明显音画异常。

## 6. 本阶段「好用」的完成标准

以下是本项目制定的初步准入标准，不是厂商保证，也不是长期可靠性证明。

### 6.1 真正四机，而不只是四台繁忙

四台 image ID、模型哈希和关键配置一致；四个唯一 rank 属于同一进程组。保存同一 job 的时间窗口、四节点计算与通信日志、真实输出。不能只凭 GPU 利用率、API 可达或 HTTP 200 判断成功。[R1]

### 6.2 正常质量，而不只是低步数测试

先连续完成 3 条正式 T2VA。之后完成一组 10 条混合任务：5 条 T2VA、5 条单首帧 FL2VA，全部串行。使用多个 prompt / seed，输入图片为用户有权使用的测试素材。

记录全部尝试，不能删除失败后重新计数。软件稳定性和生成质量分开评价：请求失败、损坏输出、节点掉线属于运行问题；可解码但角色动作不符合要求属于生成质量问题，也要保留。

首帧测试按原文档第 12.1 节执行。先验证当前镜像实际接受的素材 URI、访问范围与输入 schema；未核实前不要虚构 `file://` 支持或自动暴露公开素材服务。[R1]

### 6.3 一个入口、明确排队、不会重复生成

第一版可以继续用已有 API 客户端，不必先搭复杂 Web UI。但最终交付必须做到：

- **全群**只允许一个活跃生成任务，而不仅仅是某一个客户端单线程；入口要序列化提交，未获调度许可的额外提交须排队或明确拒绝。
- 保存任务的 prompt、seed、输入引用、完整参数、job ID、提交时间、状态、输出路径和错误原因。
- 客户端超时先查询同一 job。POST 后响应丢失且无法确认是否创建任务时，标记“状态未知、待核对”，禁止自动再发 POST 造成重复生成。
- 初期只保留一个提交入口。需要统一队列时优先复用现有调度层；没有则增加最小持久化队列，并测试重启恢复。不能把上游已有 HTTP 接口等同于上述能力已实现。

可采用 `queued / running / completed / failed / interrupted / unknown` 状态。外层任务只有在输出保存和完整解码成功后才标为可交付；后端先标记完成并不能替代这一步。

### 6.4 可以停止和恢复

通过实际 supervisor / Gateway 管理启动与暂停。固定记录 start、stop、status 和恢复方法，不要绕过已有管理层启动第二份模型。

安排一次受控的任务中断测试：先停止新任务进入，保存 job 与日志；停止本次四机 H3，确认四个 rank 都退出；恢复四机服务，再成功生成一条正式任务。被中断作业标为 interrupted / unknown，不承诺从原去噪步断点续算。

任一 rank 出错时停止继续派发，收集四台日志。不要无限重启某个 worker 或悄悄重提交所有队列任务。

### 6.5 服务访问范围清楚

初期保留原文档 localhost API 绑定，通过现有授权方式访问。需要局域网 UI 时，明确设置访问控制后再开放；不要为方便把未经鉴权的服务直接暴露到公网。

## 7. 网络通过与速度通过分开记录

TCP 诊断出片可以帮助定位问题，但必须标成 `PASS_TCP_FUNCTIONAL`，不能写成 RoCE 已验收。正式目标是本次真实作业的 RDMA 路径有证据，并完成上述使用验收。[R1]

若 TCP 能生成、RDMA 不通，阶段结论就是“计算链路通过、RDMA 阻塞待修”，继续定位现有网络或插件兼容性，不擅自购买交换机或以四个独立实例替代目标。

本阶段记录实际端到端耗时及编码、去噪、VAE 等可取得的分项时间。**不把上一轮 15–30 分钟等推算写成验收要求或实测。** 暂不要求四机必须快于双机才允许交付初步功能；明显停滞、持续换页或通信故障仍必须修复。

## 8. 不做的事情

不删除 DeepSeek / Qwen 权重、旧镜像和缓存；不重写已经工作的网络；不执行全局 Docker 清理、批量杀 Python、清空防火墙或地址；不绕过 Gateway / supervisor；不把 128GB×4 当作透明显存池。

GPU 测试与现有大模型服务如何互斥，应先在现场管理层落实。停服和任何可能断开连接的网络修改都应有明确授权与回退办法。

性能优化阶段再逐项讨论 Turbo、缓存、编译、更多并发和其他分区。每增加一个变量都保留原基线，不把它们加入本阶段首次验收。
